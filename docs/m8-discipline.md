## 2. 角色与权限

| 角色 | 可以做 | 不可以做 |
|---|---|---|
| **Lead（主对话）** | 拆任务、写任务卡、冻结接口、写共享文件、集成、跑最终门禁、提交、写报告、与用户沟通 | 把冻结面/共享文件/集成下放；让子代理自行拆任务 |
| **teammate / subagent** | 只做分到的一张卡：在自己的写作用域内改文件、跑该卡验收、留证据、按格式回报 | **再派发任何子任务**；git/发布/CI；改共享文件；动冻结面；改基线；联系用户；擅自开始下一张卡 |

> **唯一派发权在 Lead**。任何参与者发现“卡太大/需要拆分/需要更多人手”，**停止并回报 Lead**，不得自行找人或用工具再派发。M8 并行度 ≤3，Lead 直接用任务板 + `spawn_teammate` 派卡，不用多级编排。

## 3. 任务派发纪律（核心）

### 3.1 一卡一交付

- 一张卡 = 一个可独立验收的交付物（一组文件 + 单测/证据）；
- 单卡预估 **≤1 天**、改动文件 **≤8 个**（超出则拆卡）；
- 一张卡只属于一个阶段（A/B/C/D），**不跨阶段**；
- 卡与卡之间写作用域互斥，共享文件（`params.h`、`pipeline.h`、`SCHEMA.md`、`smoke_probes.cpp` 等）**只由 Lead 写**。

### 3.2 任务卡必填字段（缺一不可）

| 字段 | 要求 |
|---|---|
| **ID / 标题** | `A1：JXL 目录数据 + 规则` 这种可定位格式；标题即交付物 |
| **目标** | 一句话，可验收；不用“完善/优化/处理一下” |
| **背景与真源** | 必读文档章节 + 相关源码路径；不写“参考对话/上文” |
| **输入** | 精确文件路径、接口/契约、数据格式、依赖版本 |
| **写作用域（允许）** | 精确到文件/目录的**白名单**；不得用“相关文件”这种表述 |
| **禁止修改/禁止操作** | 精确黑名单（含共享文件、冻结面、基线、CI、依赖） |
| **接口/契约** | 函数签名、结构体字段、objectName、JSON schema；标注“已冻结/可加性/禁止改” |
| **实现约束** | 编码规范、性能/内存上限、错误文案、语言、线程模型、不得新增依赖 |
| **验收命令 + 期望** | 可复制粘贴；期望输出逐字或区间；逐条编号 |
| **证据** | 日志/截图/数据保存到 `build/m8/<task-id>/`；报告引用路径 |
| **依赖/顺序** | `blocked_by` 任务 ID；无依赖则写“无” |
| **时间盒** | 预计半天/1 天；超时点 |
| **停止条件** | 遇到什么必须停下报告（接口冲突、需要改冻结面、需要新增依赖、验收不可达、发现范围外问题） |
| **报告格式** | 固定：状态 / 变更文件 / 验收结果（命令+输出）/ 偏差 / 未覆盖与风险 / 下一步 |

### 3.3 “清晰”的判定标准（Lead 派卡前自检）

1. 不看对话，只看这张卡能否独立完成；
2. 每条验收命令都能复制执行，期望结果可机械判定；
3. 每个键名/文件名/objectName/字符串**逐字精确**；
4. 至少列出一个正例、一个边界例、一个反例（如适用）；
5. 明确“不做什么”（非目标）；
6. 明确失败时怎么办（停止/回报/不得猜）；
7. 不存在“视情况/适当/尽量/参考现有实现”这类模糊词；
8. 写作用域与禁止项无歧义；
9. 单卡 ≤1 天、≤8 文件；
10. 依赖关系与阶段边界明确。

> **反例（不合格）**：“把 JXL 参数补全，注意联动。”——无范围、无验收、无写作用域。
> **正例**：“A1：写 `jxl_catalog.inc` 的 16 个新键行；每行含 key/type/domain/default/label/group/status/control/role/reason；只改该文件；验收：`test_param_catalog` 对账 0 差异 + `x265` 同名键不得出现；证据：`build/m8/a1/`。”

### 3.4 子代理的退回权

- 任务卡不清晰/自相矛盾/缺验收/写作用域与依赖冲突 ⇒ **立即停止，回报 Lead**，不得自行猜测、不得扩大范围、不得“先做起来再说”。
- Lead 修订任务卡后重新派发；原卡作废并留记录。

### 3.5 任务板是唯一真源

- 所有任务先建共享任务卡（含写作用域/依赖/验收），再 `claim`，完成后 `complete` 并附报告摘要；
- 消息只作补充，**与任务板冲突时以任务板最新 revision 为准**；
- 子代理不得自行改任务范围/依赖/写作用域；需要变更 ⇒ 回报 Lead。

## 4. 写作用域与构建纪律

1. **一卡一构建树**：`build/m8/<task-id>/`，配置带 `-DVCPKG_MANIFEST_INSTALL=OFF`；不得用别人的构建树、不得并发写 vcpkg。
2. **最终门禁统一在 `build/release-dev` 由 Lead 跑**；子卡只跑自己的单测/小语料。
3. **禁止全仓格式化/全仓 search-replace**；只格式化自己改的文件。
4. **禁止改**：`tests/golden/**` 夹具与 `SCHEMA.md`（除 Lead 的加性任务）、`tools/baseline/**`、CI 文件、依赖清单、overlay、triplets、冻结文件（除 Lead 的加性追认任务）。
5. **禁止 `regression.py --update`**；禁止改断言“让它变绿”；禁止删除测试。
6. 新增/删除文件必须在任务卡的写作用域内；删除任何文件前必须 Lead 确认。
7. 临时探针/脚本只放 `build/m8/<task-id>/`（gitignored），不入库。

---

## 5. 证据与报告纪律

- 每个验收命令都要留 `cmd.log`（或等价证据），报告引用**路径 + 关键输出行**；
- UI 改动留截图/探针输出；数值/性能留数据文件与命令；
- 报告固定格式：
  ```
  状态：完成 / 部分完成 / 阻塞
  变更文件：<精确列表>
  验收：<命令> → <结果>（逐条对应任务卡）
  偏差：<与任务卡/契约的差异 + 原因>
  未覆盖/风险：<如实，不粉饰>
  下一步：<建议/需要 Lead 决策的点>
  ```
- **没跑的命令不许写“通过”**；失败/偏差必须如实写；不允许“看起来完成了”。

---

## 6. 阶段、门禁与集成纪律

1. **阶段串行**：K → A → B → C → D；上一阶段门禁全绿 + Lead 验收后才进下一阶段；**不跨阶段抢跑**。
2. **接口先冻结**：A0 冻结 `.inc`/`catalog.h`；B0 冻结 `params.h` 加性与 `paramform.h` 接口；C0 冻结指标 API/SCHEMA 草案。冻结后变更必须 Lead 裁定 + 登记。
3. **每阶段一个可回滚提交**（`M8-A`/`M8-B`/`M8-C`），收口提交不入发行 tag；子代理不提交。
4. **门禁失败**：先归因；修复优先于放宽；禁止重播种；确需改判据 ⇒ Lead 向用户确认。
5. **集成只由 Lead 做**：合并、解决冲突、跑全量门禁、写报告；子卡之间不得互相改文件。
6. **每日同步**：卡状态 / 门禁 / 风险 / 阻塞；超时 0.5 天必须升级。

---

## 7. 沟通纪律

- 消息自包含（含任务 ID、文件路径、命令、期望）；以发送者名字开头（运行时自动）；
- 子代理只向 Lead 汇报，不联系用户；
- 不假设“对方知道上下文”；引用文档给路径+章节；
- 发现范围外问题：记录并回报，不顺手改；
- 决策写进 `docs/m8-adjudications.md`，不靠聊天记忆。

---

## 8. 子任务禁止再派发的执行细则

1. teammate/subagent **不得调用**：`spawn_teammate`、`subagent`、`subagent_fork`、`workflow` 或任何等价编排机制；
2. 不得通过 `pwsh`/脚本/子进程启动另一个 agent；
3. 不得把任务“转交”给另一个 teammate（包括直接发消息请求帮忙）；
4. 任务过大/需要并行 ⇒ 回报 Lead，由 Lead 拆卡并派发；
5. 违反即：中断当前任务、撤销产出、记录 `m8-adjudications.md`；重复违反不再派卡。

> 说明：Agent Teams 的工具权限本身只允许 Lead 派发；本纪律把它变成**团队约定 + 验收项**，防止“事实可行但流程越界”。

---

## 9. 违规处理

| 情形 | 处理 |
|---|---|
| 未开工写实现 / 越界改文件 | 回滚 + 记录 + 重派 |
| 改冻结面未追认 | 返工 + 补裁定 |
| 改基线/放宽断言 | 回滚 + 记录；不放行 |
| 递归派发 | 中断 + 撤销产出 + 记录 |
| 无证据报完成 | 视为未完成；重跑验收 |
| 隐瞒失败/偏差 | 记录；该卡重新验收 |
